## 3. Hallazgos por Categoría

### 3.1 MEM — Memory Safety / Fugas / UB

#### `MEM-001` [ALTA] `Box::leak` en carga de plugins FFI
- **Archivo:** `src/plugins/ffi.rs:120`
- **Código:**
  ```rust
  let cached_name = Box::leak(name_str.into_boxed_str());
  ```
- **Impacto:** Cada plugin FFI cargado fuga permanentemente el nombre en el heap. En cargas dinámicas repetidas (recon en caliente) esto acumula memoria no recuperable.
- **Remediación:** Usar `String` o `Cow<'static, str>` y almacenar el nombre en el struct en lugar de forzar `'static` via leak.

#### `MEM-002` [CRÍTICA] `Box::leak` en hot path de `WasmPlugin::name()`
- **Archivo:** `src/core/plugin_loader.rs:294`
- **Código:**
  ```rust
  fn name(&self) -> &'static str {
      Box::leak(self.name.clone().into_boxed_str())
  }
  ```
- **Impacto:** **Cada llamada** a `name()` clona el string y lo fuga. En un bucle de enumeración con cientos de plugins WASM, esto genera una fuga lineal ilimitada. Peor que `MEM-001` porque ocurre en hot path, no solo en carga.
- **Remediación:** Pre-calcular `&'static str` en el constructor del plugin y almacenarlo. O cambiar el trait `ScannerPlugin::name()` para devolver `String` o `Arc<str>`.

#### `MEM-003` [CRÍTICA] Uso de `ManuallyDrop<Vec>` sobre memoria `mmap` sin verificación de `munmap`
- **Archivo:** `src/core/net_evasion/af_xdp_channel.rs:233-248`
- **Código:**
  ```rust
  impl Drop for AfXdpChannel {
      fn drop(&mut self) {
          unsafe {
              let ptr = self._tx_ring.as_ptr() as *mut libc::c_void;
              let size = TX_RING_SIZE * std::mem::size_of::<libc::xdp_desc>();
              libc::munmap(ptr, size);  // ← retorno ignorado
              std::mem::ManuallyDrop::drop(&mut self._tx_ring);
              libc::close(self.sock);
          }
      }
  }
  ```
- **Impacto:** Si `munmap` falla (errno), `ManuallyDrop::drop` ejecuta `Vec::drop` sobre memoria ya mapeada, provocando **doble liberación / UB**. Además, `libc::close` no verifica errores.
- **Remediación:** Verificar retorno de `munmap`. Si falla, no ejecutar `ManuallyDrop::drop`. Considerar usar `std::os::unix::io::OwnedFd` para el socket.

#### `MEM-004` [ALTA] `unsafe impl Send` sin garantías de thread-safety
- **Archivo:** `src/plugins/ffi.rs:177-178`
- **Código:**
  ```rust
  struct SendPtr(*mut FFIFindings);
  unsafe impl Send for SendPtr {}
  ```
- **Impacto:** El puntero `*mut FFIFindings` proviene de un plugin externo C/Rust. No hay garantía de que el plugin no use TLS (Thread-Local Storage) o estructuras no thread-safe. `spawn_blocking` mueve este puntero a otro thread sin validación.
- **Remediación:** Documentar el contrato FFI explícito: "El plugin debe garantizar que `FFIFindings` sea thread-safe". O mejor: no usar `spawn_blocking` para FFI; ejecutar en un proceso sandboxed separado (seccomp, namespaces).

#### `MEM-005` [CRÍTICA] `process::exit(1)` rompe graceful shutdown
- **Archivo:** `src/utils/memory_monitor.rs:99`
- **Código:**
  ```rust
  if curr > hard {
      error!("CRITICAL: Memory {}MB/{}MB, triggering shutdown signal", curr, hard);
      std::process::exit(1);
  }
  ```
- **Impacto:** Tokio no completa su shutdown sequence. Sockets TCP quedan en `TIME_WAIT`, archivos temporales no se eliminan, procesos hijos (nmap, sqlmap, etc.) quedan huérfanos/zombis. En un entorno de bug bounty, esto puede dejar reglas iptables persistentes (`TcpSession`) o proxies SOCKS activos.
- **Remediación:** Emitir un `CancellationToken::cancel()` al `ShutdownManager` existente y esperar a que los hooks de limpieza terminen (con timeout).

#### `MEM-006` [ALTA] `tokio::spawn` dentro de `Drop` no garantiza ejecución
- **Archivo:** `src/utils/process_guard.rs:76`
- **Código:**
  ```rust
  impl Drop for ExternalToolGuard {
      fn drop(&mut self) {
          if let Ok(mut pid_guard) = self.child_pid.try_lock() {
              if let Some(pid) = pid_guard.take() {
                  tokio::spawn(async move {
                      let _ = crate::utils::common::kill_pgid(pid).await;
                  });
              }
          }
      }
  }
  ```
- **Impacto:** Si el runtime se está apagando, `tokio::spawn` puede no ejecutar la tarea. Procesos hijos (hydra, nmap, etc.) permanecen como zombis. Además, `try_lock` en `Drop` puede fallar si otro thread tiene el lock.
- **Remediación:** Usar `kill_pgid_sync` (síncrono) en `Drop`. El código ya tiene `kill_pgid_sync` definido en `common.rs:154`; usarlo aquí.

#### `MEM-007` [MEDIA] `RwLock::read().unwrap()` puede paniquear si el lock está envenenado
- **Archivo:** `src/core/mcp/sanitizer.rs:265`
- **Código:**
  ```rust
  pub fn unmask_input(&self, text: &str) -> String {
      let mut real_text = text.to_string();
      let mapping = self.mask_to_real.read().unwrap();
      ...
  }
  ```
- **Impacto:** Si un thread anterior paniquea mientras sostiene el `write` lock, el lock se envenena y `read().unwrap()` provoca pánico en tiempo de ejecución. Esto es un DoS del MCP server.
- **Remediación:** Usar `read().unwrap_or_else(|e| e.into_inner())` para recuperarse del poison, o migrar a `tokio::sync::RwLock`/`parking_lot::RwLock`.

#### `MEM-008` [MEDIA] `expect` en registro de handler de señales
- **Archivo:** `src/core/net_evasion/tcp_session.rs:37`
- **Código:**
  ```rust
  let mut signals = signal_hook::iterator::Signals::new([...])
      .expect("Failed to register signal handler");
  ```
- **Impacto:** En entornos restringidos (contenedores sin capacidad `CAP_KILL` o con seccomp), el registro de señales puede fallar y provocar pánico inesperado.
- **Remediación:** Cambiar a `?` o `map_err` y propagar el error al caller.

### 3.2 SEC — Seguridad / Bug Bounty / Exploitability

#### `SEC-001` [ALTA] Crecimiento ilimitado de `BTreeMap` en `DataSanitizer`
- **Archivo:** `src/core/mcp/sanitizer.rs:279-284`
- **Código:**
  ```rust
  let count = r2m.len() + 1;
  let mask = format!("{}_{}", prefix, count);
  r2m.insert(real.to_string(), mask.clone());
  m2r.insert(mask.clone(), real.to_string());
  ```
- **Impacto:** En una ejecución prolongada (swarm continuo), cada IP/dominio único encontrado se almacena permanentemente. Esto es un vector de DoS por memoria: un atacante que controle la salida de un plugin puede forzar IPs/dominios arbitrarios y agotar la RAM.
- **Remediación:** Implementar un límite de capacidad (LRU cache, ej. `lru::LruCache`) o TTL de expiración para entradas de enmascaramiento.

#### `SEC-002` [ALTA] `ptr::read` + `from_raw_parts` sin validación de alineación
- **Archivo:** `src/plugins/ffi.rs:214-232`
- **Código:**
  ```rust
  let ffi_findings = std::ptr::read(findings_ptr);
  let slice = if ffi_findings.len > 0 {
      std::slice::from_raw_parts(ffi_findings.data, ffi_findings.len)
  } else { &[] };
  ```
- **Impacto:** Un plugin malicioso o corrupto puede devolver un puntero no alineado a `FindingFFI`. `ptr::read` de datos no alineados es **UB inmediato** en Rust. No hay validación de `align_of::<FindingFFI>()`.
- **Remediación:** Verificar alineación antes de `ptr::read`: `findings_ptr as usize % align_of::<FindingFFI>() == 0`. Lo mismo para `ffi_findings.data`.

#### `SEC-003` [MEDIA] Verificación de path traversal redundante y débil
- **Archivo:** `src/core/plugin_loader.rs:111-122`
- **Código:**
  ```rust
  let canonical_path = std::fs::canonicalize(path)?;
  ...
  if path_str.contains("..") {
      anyhow::bail!("Security Violation...");
  }
  ```
- **Impacto:** `canonicalize` ya resuelve `..`. La verificación posterior del string es redundante. No es un bypass directo, pero indica falta de rigor en el modelado de amenazas del loader.
- **Remediación:** Eliminar la verificación redundante y documentar explícitamente que `canonicalize` es la única fuente de verdad.

#### `SEC-004` [ALTA] Ausencia de sandbox para código de red de bajo nivel
- **Archivos:** `src/core/net_evasion/tcp_session.rs`, `raw_socket.rs`, `quic_forge.rs`, `ja4_spoofer.rs`
- **Impacto:** El código manipula raw sockets, iptables, y forja paquetes TCP/QUIC. Un bug (off-by-one en `packet_forge`, race condition en `iptables -A`/`-D`) puede causar denegación de servicio local, bloqueo de tráfico legítimo, o filtración de paquetes malformados. No hay seccomp, namespaces de red, ni dropping de capabilities.
- **Remediación:** Ejecutar componentes de net evasion en un proceso separado con `seccomp-bpf`, `CLONE_NEWNET`, y `CAP_NET_RAW`/`CAP_NET_ADMIN` dropeados después de inicializar sockets.

#### `SEC-005` [MEDIA] `Signature::from_slice` no verifica longitud en compile-time
- **Archivo:** `src/core/web/state.rs:52`
- **Código:**
  ```rust
  let signature = Signature::from_slice(signature_bytes)
      .map_err(|_| (StatusCode::UNAUTHORIZED, "Invalid signature format".to_string()))?;
  ```
- **Impacto:** `from_slice` acepta slices de cualquier longitud y falla si no es 64 bytes. La verificación manual de longitud (línea 47: `token_bytes.len() != 96`) mitiga el problema, pero el flujo debería ser más robusto.
- **Remediación:** OK como está, pero considerar usar `TryFrom<&[u8]>` con tipos de longitud fija.

### 3.3 CONC — Concurrencia / Async / Sincronización

#### `CONC-001` [CRÍTICA] `LockFreeResultSink` descarta objetivos silenciosamente
- **Archivo:** `src/core/lock_free_sink.rs:71-77`
- **Código:**
  ```rust
  pub fn enqueue(&self, target: TargetHost) {
      if let Err(t) = self.queue.push(target) {
          error!("⚠️  v4-SINK: Results queue is FULL ... Dropping target {}", t.host);
      }
  }
  ```
- **Impacto:** En un escaneo de bug bounty, perder un objetivo equivale a perder un hallazgo potencial. El sistema no ofrece backpressure real ni mecanismo de reintento.
- **Remediación:** Implementar backpressure con `tokio::sync::mpsc::bounded_channel` o bloqueo cooperativo (`tokio::task::yield_now`) cuando el queue esté >90% de capacidad.

#### `CONC-002` [ALTA] `tokio::sync::Mutex` en `SwarmOrchestrator` causa contención
- **Archivo:** `src/core/orchestrator/swarm/coordinator.rs:28,60,108,168`
- **Código:**
  ```rust
  pub engagement: Arc<tokio::sync::Mutex<Option<EngagementState>>>,
  let correlation_engine = Arc::new(tokio::sync::Mutex::new(ce_inner));
  ```
- **Impacto:** Cada agente swarm debe adquirir el lock de `engagement` y `correlation_engine`. Con 10+ agentes concurrentes (semaphore línea 69), esto serializa operaciones que podrían ser lock-free (ej. `DashMap` para engagement state).
- **Remediación:** Para `engagement`, usar `ArcSwap` o `DashMap` si la estructura lo permite. Para `correlation_engine`, considerar `RwLock` o desacoplar lecturas de escrituras.

#### `CONC-003` [MEDIA] Condición de carrera en reset de presupuesto (`api_budget.rs`)
- **Archivo:** `src/utils/api_budget.rs:44-96`
- **Código:**
  ```rust
  if should_reset {
      self.used.store(0, Ordering::Release);
      self.last_reset.store(now, Ordering::Release);
  }
  ```
- **Impacto:** Dos operaciones `Release` separadas no son atómicas. Un thread puede observar `used==0` pero `last_reset` aún con el valor antiguo (o viceversa), permitiendo un gasto doble en la ventana de reset.
- **Remediación:** Agrupar el estado de reset en un único `AtomicU64` (timestamp + used como campos bitpacked) o usar `Mutex` para la secuencia de reset.

#### `CONC-004` [MEDIA] `std::sync::Mutex` bloquea threads del runtime Tokio
- **Archivos:**
  - `src/core/native_scanner.rs:35` (`std::sync::Mutex<IoUring>`)
  - `src/utils/resource_manager.rs:34` (`std::sync::Mutex<System>`)
  - `src/infrastructure/proxy/manager.rs:71` (`std::sync::MutexGuard` expuesto públicamente)
  - `src/core/net_evasion/orchestrator.rs:20`
- **Impacto:** `std::sync::Mutex` en funciones `async` bloquea el thread del worker Tokio si el lock está contencionado. Esto reduce throughput y puede causar timeouts en otros tasks.
- **Remediación:** Migrar a `tokio::sync::Mutex` cuando el lock se sostenga a través de `.await`, o reestructurar para no cruzar await boundaries con el lock activo.

### 3.4 PERF — Rendimiento / Optimización

#### `PERF-001` [ALTA] Duplicación de `rustls` (0.21 + 0.23)
- **Archivo:** `Cargo.toml:79,85`
- **Código:**
  ```toml
  rustls = "0.21"
  rustls-ech = { package = "rustls", version = "0.23" }
  ```
- **Impacto:** Dos versiones de `rustls` en el árbol de dependencias duplican código TLS, aumentan el tamaño binario (~500KB-1MB estimado) y pueden causar conflictos de tipos si se mezclan APIs en el mismo módulo.
- **Remediación:** Unificar a `rustls 0.23` y eliminar el alias `rustls-ech`. Actualizar `reqwest` a 0.12 (que usa rustls 0.23) para compatibilidad.

#### `PERF-002` [MEDIA] Dependencias obsoletas / deprecadas
- **Archivo:** `Cargo.toml`
- **Lista:**
  - `reqwest 0.11` → 0.12 disponible
  - `toml 1.1.2` → 0.8.x es la línea actual (nota: `toml` crate versioning cambió)
  - `dotenv 0.15.0` → `dotenvy` es el fork mantenido
  - `once_cell 1.21.3` → funcionalidad ahora en `std::sync::LazyLock` (Rust 1.80+)
- **Impacto:** Deuda técnica, potenciales CVEs no parchados, incompatibilidades futuras.
- **Remediación:** Actualizar `reqwest`, migrar `dotenv`→`dotenvy`, evaluar eliminar `once_cell` en favor de `std`.

#### `PERF-003` [MEDIA] Compilación LTO + codegen-units=1 ralentiza builds de desarrollo
- **Archivo:** `Cargo.toml:143-147`
- **Código:**
  ```toml
  [profile.release]
  opt-level = 3
  lto = true
  codegen-units = 1
  strip = true
  ```
- **Impacto:** `codegen-units = 1` + `lto = true` maximiza optimización pero compila todo en un único CGU, ralentizando builds incrementales drásticamente.
- **Remediación:** Considerar `codegen-units = 16` para builds de CI/development, manteniendo `codegen-units = 1` solo para releases finales (usar un perfil `profile.production` separado).

### 3.5 ARCH — Arquitectura / Mantenibilidad / Profesionalidad

#### `ARCH-001` [MEDIA] Ausencia de `#![deny(unsafe_code)]` en módulos seguros
- **Archivo:** Múltiples módulos (`core/ai`, `core/sink`, `plugins/reporting`, etc.)
- **Impacto:** `unsafe` puede introducirse accidentalmente en módulos que no deberían usarlo. Actualmente hay ~798 ocurrencias de la palabra "unsafe" (incluyendo comentarios y strings).
- **Remediación:** Añadir `#![deny(unsafe_code)]` a los `lib.rs` o `mod.rs` de módulos que no requieren unsafe (ej. AI, sinks, reporting). Solo los módulos de red evasion y FFI deberían permitirlo.

#### `ARCH-002` [MEDIA] Sin `cargo-audit` / `cargo-deny` configurado
- **Archivo:** N/A (ausencia)
- **Impacto:** No hay detección automática de CVEs en dependencias ni política de licencias.
- **Remediación:** Añadir `cargo-audit` al CI (`.github/workflows/parity.yml`) y un `deny.toml` para políticas de dependencias.

#### `ARCH-003` [BAJA] Tests con `#[ignore]` sin feature gates adecuados
- **Archivo:** Múltiples (ej. `src/core/net_evasion/raw_socket.rs:127`, `src/core/net_evasion/tcp_session.rs` implícito)
- **Impacto:** La suite de tests no se ejecuta completamente en CI. El workflow `parity.yml` no ejecuta `cargo test` ni `cargo clippy`.
- **Remediación:** Migrar tests que requieren privilegios a feature flags (`#[cfg(feature = "integration-cap-net-raw")]`) y ejecutar la suite completa en CI con runners con capacidades adecuadas.

#### `ARCH-004` [BAJA] `unwrap` / `expect` en tests de lógica de negocio
- **Archivo:** `src/core/tests.rs:215,228,263,etc.`
- **Impacto:** Los tests del core usan `.unwrap()` para acceder a JSON comprimido. Si la estructura cambia, el test paniquea sin mensaje descriptivo.
- **Remediación:** Usar `?` en tests `Result`-based o `assert!(...is_some(), "...")` con mensajes descriptivos.

#### `ARCH-005` [MEDIA] `DashMap` + `Arc<tokio::sync::Mutex>` mezclados sin estrategia clara
- **Archivo:** `src/core/orchestrator/swarm/coordinator.rs`, `src/core/web/state.rs`
- **Impacto:** Hay inconsistencia en la elección de primitivas de concurrencia. `DashMap` es lock-free para reads, pero `tokio::sync::Mutex` bloquea async tasks. La arquitectura no define cuándo usar cada uno.
- **Remediación:** Documentar una "Concurrency Policy": `DashMap` para caches/read-heavy, `tokio::sync::RwLock` para state mutable poco frecuente, `tokio::sync::Mutex` solo cuando se requiera exclusión mutua a través de await.
